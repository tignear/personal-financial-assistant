# 設計ドキュメント規約 (Design Document Policy)

* **作成日**: 2025年6月16日

## 1. 概要 (Overview)
このプロジェクトにおける設計思想と意思決定プロセスを記録し、共有するため、Gitで管理できる軽量なデザインドキュメント規約を導入する。本規約は、単なる仕様の記録ではなく、**特に「なぜ」という意思決定のプロセスを記録すること**に主眼を置いている。

## 2. 背景と目的 (Why)
このプロジェクトは始まったばかりであり、今後自分たち自身がメンテナンスを行う際や、新しいコントリビューターが参加してくれる際に、「なぜ、そのように実装されているのか？」という設計の背景が失われることを防ぐ必要がある。

この「なぜ」が不明確だと、過去の経験から、以下のような問題が発生することが分かっている。
* メンテナンスや機能追加の際に、意図しない仕様変更（デグレード）を引き起こすリスクが高まる。
* プロジェクトの全体像が掴みにくくなり、新しい参加者の学習コストが増大する。

そこで、誰でもプロジェクトの技術的な背景と思想を理解できる状態を作ることを目的として、本規約を定める。

## 3. 提案する設計 (How)
### 3.1. ドキュメントフォーマット
設計に関するドキュメントは以下のMarkdownテンプレートを基本とする。

```markdown
### 1. 概要 (Overview)
*【この設計が解決する課題と、その解決策の要点を1〜3行で記述する】*

### 2. 背景と目的 (Why)
*【なぜこの設計が必要になったのか、どのようなユーザー課題や技術的課題を解決するのかを具体的に記述する。Issueへのリンクを貼ると良い】*

### 3. 提案する設計 (How)
*【アーキテクチャ図、シーケンス図、データモデルなど、設計内容を記述する。最初は手書きの図の写真でも良い。完璧を目指さない】*
* 3.1. ハイレベルデザイン
* 3.2. 詳細（必要に応じて）

### 4. 設計上の意思決定 (Architectural Decision Records - ADR)
*【このドキュメントの核となる最重要セクション。ツールの選定やAPIの設計といった具体的な「結果(How)」だけでなく、その結論に至るまでの「なぜ(Why)」、つまり背景、検討した代替案、そして最終的な採用理由といった意思決定のプロセスそのものを記録する】*

* **決定事項**: 
* **背景・課題**: 
* **検討した代替案**:
* **採用理由**: 


### 5. 補足
*【懸念事項、未解決の問題、将来的な拡張案などがあれば記述する】*
```

3.2. 運用ルール

    いつ書くか？ -> 実装の着手前、または並行して
        原則（着手前）: 新機能やアーキテクチャの変更など、影響の大きな開発に着手する前に、このドキュメントのドラフトを作成します。そして、チームで設計方針のレビューと合意形成を行ってから、実装を開始します。
        例外（並行）: 小さな改善や、設計が自明なタスクの場合は、実装と並行して作成しても構いません。ただし、Pull Requestをマージする前までには必ずドキュメントを完成させ、コードと一緒にレビューすることを必須とします。

    mainブランチへのマージが「承認」の証
        mainブランチに存在するドキュメントは、チームの公式な決定事項（承認済み）として扱います。ファイル内にステータスを明記する必要はありません。

    古くなったら -> 「非推奨」を追記する
        設計が古くなった場合は、新しいPull Requestを作成し、ドキュメントの最上部に以下のような「非推奨ヘッダー」を追記します。
        Markdown

        > **[非推奨]** この設計は古くなっています。
        > 新しい設計は [こちら](link/to/new/doc) を参照してください。

    完璧を目指さない（ただし、思想は記録する）
        最初からすべての項目を完璧に埋める必要はありません。特に**「4. 設計上の意思決定 (ADR)」セクションを、たとえ短い文章でも良いので自分の言葉で書くことに最も価値があります。**

4. 設計上の意思決定 (Architectural Decision Records - ADR)

この規約自体を定めるにあたっての、最も重要な意思決定を以下に記録する。

    決定事項:
    設計ドキュメントでは、最終的な仕様の網羅性（結果）よりも、**「なぜその仕様になったか（意思決定のプロセス）」**の記録を最優先事項とする。

    背景・課題:
    過去のプロジェクトの経験から、詳細な仕様書が存在しても、その背景にある「トレードオフの考慮」や「採用されなかった代替案」の情報が失われていると、メンテナンスや仕様変更が非常に困難になる。仕様はコードを読めばある程度推測できるが、「なぜ」はコードには現れない。この「なぜ」の欠落が、技術的負債の温床となっていた。

    検討した代替案:

        案A: 従来型の詳細な仕様書を指向する
            メリット: すべての仕様が網羅され、QAのテストケース作成などには役立つ。
            デメリット: 記述・メンテナンスコストが非常に高く、すぐに時代遅れになる。開発のスピードを阻害し、結局形骸化しやすい。「なぜ」が記録されにくい。

        案B: ドキュメントは書かず、コードとコメントで表現する
            メリット: 開発スピードが最速。情報が常に最新（コードが正）。
            デメリット: アーキテクチャレベルの大きな設計思想や、複数の選択肢から検討した結果（ボツ案の情報）など、コードに現れないコンテキストを記録することが困難。

    採用理由:
    プロジェクトの長期的な健全性とメンテナンス性は、個々の仕様の正しさよりも**「設計思想の継承」**に強く依存すると判断した。「意思決定のプロセス」を記録することが、最もコストパフォーマンスが高く、将来の自分たちやコントリビューターにとって有益な知識継承の方法であると結論付けた。この方針決定が、後のツール選定（Git Markdown採用）にも繋がっている。

5. 補足

このドキュメント規約自体も、絶対的なものではない。プロジェクトの成長に合わせて、より良い方法が見つかれば改善していく。改善案はいつでもIssueやPull Requestで歓迎する。ただし、何でも書こうとしないこと!ルールが自動的にカルチャーを作るわけではないので。
