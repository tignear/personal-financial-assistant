# MVPにおけるコマンドとイベントの具体的な設計 (MVP Command & Event Design)

* **作成日**: 2025年6月16日

## 1. 概要 (Overview)
このドキュメントは、財務管理BotのMVP（Minimum Viable Product）において、「取引の記録 (`/add` コマンド)」と「残高確認 (`/status` コマンド)」を実現するために必要となる、具体的なコマンドとイベントの構造を定義します。MVPでは、Event Sourcingアーキテクチャの核となる部分に焦点を当て、最小限のデータモデルで機能を実現します。

## 2. 背景と目的 (Why)
MVP開発方針に基づき、早期に価値を提供し、共同開発者との効率的な連携を目指します。そのために、Event Sourcing + CQRSアーキテクチャの導入を段階的に行い、まずはコアとなる「取引記録」とそれに基づく「残高確認」の機能から着手します。このドキュメントは、これらの機能を実現するための具体的なメッセージ（コマンドとイベント）の構造を定義し、実装の共通認識を形成することを目的とします。特に、「過去の取引履歴の消失」という本質的な課題解決に焦点を当て、会計データの不変性をイベントを通じて確保します。

## 3. 提案する設計 (How)

### 3.1. ハイレベルデザイン
MVPでは、以下のデータフローを想定します。

1.  ユーザーがDiscord Botを通じて `/add` コマンドを送信します。
2.  Command Sideがコマンドを受け取り、バリデーション後、`TransactionRecordedEvent` を生成します。
3.  `TransactionRecordedEvent` がEvent Store (PostgreSQL) に永続化されます。
4.  Query Side (プロジェクションサービス) がEvent Storeから `TransactionRecordedEvent` を非同期的に読み取り、`AccountBalanceProjection` (リードモデル) を更新します。
5.  ユーザーが `/status` コマンドを送信します。
6.  Query Sideが `AccountBalanceProjection` から情報を読み取り、ユーザーに応答します。

### 3.2. 詳細

#### 3.2.1. コマンド定義

**`RecordTransactionCommand`** (Discord `/add` コマンドに対応)
ユーザーからの取引記録リクエストを表すコマンドです。

* **目的**: 日々の支出や収入を記録します。
* **発生源**: Discord Botの `/add` コマンド。
* **構造**:
    * `commandId: UUID` (コマンドの一意な識別子)
    * `userId: UserId` (コマンドを実行したユーザーのID)
    * `accountId: AccountId` (対象となる口座のID。MVPでは簡略化された口座管理を想定します。)
    * `amount: BigDecimal` (取引金額。**正の数値は収入**を、**負の数値は支出**を表します。金額の正負によって取引のタイプを識別します。)
    * `transactionDate: LocalDate` (取引が発生した日付。デフォルトはコマンド実行日。)
    * `tags: Set[String]` (カテゴリや付加情報。タグで可能な限り多くの情報を表現することを推奨します。)
    * `memo: Option[String]` (任意のメモ。)

#### 3.2.2. イベント定義

**`TransactionRecordedEvent`**
`RecordTransactionCommand` が成功裏に処理された結果、Event Storeに記録されるイベントです。このイベントは取引の事実を不変なものとして記録します。

* **目的**: 取引が記録された事実を永続化します。
* **発生源**: Command Side (ドメインモデル)。
* **構造**:
    * `eventId: UUID` (イベントの一意な識別子)
    * `transactionId: TransactionId` (このイベントによって生成された取引の一意なID)
    * `userId: UserId` (取引を記録したユーザーのID)
    * `accountId: AccountId` (影響を受けた口座のID)
    * `amount: BigDecimal` (取引金額)
    * `transactionDate: LocalDate` (取引が発生した日付)
    * `recordedAt: Instant` (イベントが記録された日時)
    * `tags: Set[String]` (取引に付与されたタグ)
    * `memo: Option[String]` (取引に付与されたメモ)

#### 3.2.3. リードモデル定義

**`AccountBalanceProjection`** (Discord `/status` コマンドに対応)
口座の現在の残高を高速に参照するためのリードモデル（プロジェクション）です。

* **目的**: ユーザーの口座残高を瞬時に表示します。
* **データ構造**:
    * `accountId: AccountId`
    * `currentBalance: BigDecimal`
    * `lastUpdatedAt: Instant`
* **更新ロジック**:
    * `TransactionRecordedEvent` が発行されるたびに、該当する `accountId` の `currentBalance` に `amount` を加算し、`lastUpdatedAt` を更新します。
    * 将来的には、`/adjust` コマンドによって発行されるイベントや、スケジュールドトランザクションに関するイベントもこのリードモデルの更新をトリガーします。

## 4. 設計上の意思決定 (Architectural Decision Records - ADR)

* **決定事項**: MVPにおける主要なコマンドとして `RecordTransactionCommand` を、主要なイベントとして `TransactionRecordedEvent` を定義し、これらのイベントを基に `AccountBalanceProjection` リードモデルを構築します。
* **背景・課題**:
    * MVPの目標である「取引の記録」と「残高確認」を最小限の労力で実現する必要があるためです。
    * Event Sourcingの核となる「イベントの不変性」を担保しつつ、将来的な拡張性を考慮したイベント設計が求められます。
    * ユーザーからの入力と内部的な事実（イベント）を明確に分離する必要があるためです。
* **検討した代替案**:
    * **案A: 最初に詳細なカテゴリ分類や取引タイプをコマンド・イベントに含める**:
        * メリット: 将来的な機能拡張に対応しやすいです。
        * デメリット: MVP段階での複雑性が増大し、開発期間が長期化するリスクがあります。特にタグの利用で多くの情報を表現できるため、MVPでは不要と判断しました。
    * **案B: コマンドとイベントの構造を完全に一致させる**:
        * メリット: シンプルで理解しやすいです。
        * デメリット: コマンドはユーザーからの「意図」を表し、イベントはシステム内で発生した「事実」を表すため、常に一致するとは限りません。特に、コマンドにはユーザーIDのような実行コンテキスト情報が含まれますが、イベントには取引の事実のみが含まれるべき場合があるためです。また、将来的にコマンドが複数のイベントを発行する可能性も考慮すると、構造の一致は制約となります。
* **採用理由**:
    * **MVPのスコープに厳密に準拠**: 最小限の機能で早期の価値提供を目指すため、必要最低限のコマンドとイベントに絞り込みました。これにより、開発の複雑性を抑え、共同開発者の初期参入ハードルを低く保ちます。
    * **「タグ」による柔軟性**: カテゴリを固定のEnumなどで定義せず、`Set[String]` の`tags` を採用することで、MVPの段階では柔軟な分類を可能とし、将来的なビジネス要件の変化にも対応しやすくします。これにより、機能の実装を優先し、パフォーマンス最適化や高度なエラーハンドリングをMVPの範囲外とする方針にも合致します。
    * **Event Sourcingの原則に従う**: コマンドとイベントの役割を明確に分離することで、Event Sourcingの「不変な事実の記録」という原則を遵守します。これにより、会計データの完全な監査可能性を確保するというプロジェクトの核となる思想を実現します。
    * **段階的な拡張性**: `AccountBalanceProjection` の更新ロジックをイベント駆動にすることで、将来的に `AccountAdjustedEvent` や `ScheduledTransactionProcessedEvent` などの新たなイベントが追加された際にも、既存の構造に大きな変更を加えることなくリードモデルを拡張できます。

## 5. 補足
この設計は、MVPで必要となるコア機能に焦点を当てたものです。今後の開発フェーズにおいて、ユーザーからのフィードバックや新たなビジネス要件に基づいて、コマンドやイベントの構造、およびリードモデルは柔軟に拡張される可能性があります。

**【MVP期間中のアカウントおよびタグの取り扱いについて】**

MVPでは、ユーザーがDiscord Botを通じて直接アカウントやタグを作成・管理する機能は含めません。これは、MVPのスコープを「取引の記録」と「残高確認」という核となる機能に絞り、複雑性の増大を避けるためです。

MVP期間中、アカウントおよびタグは、開発環境内での初期データ投入（設定ファイル）によって対応することを想定しています。

**【エラーハンドリングとZIOの利用について】**

コマンド処理において、**不正な入力値やビジネスルールに違反する操作は、イベントとして記録せず、ZIOのエラー型 `E` を用いてコマンドの処理段階でエラーとして返します。** これにより、イベントストアには常に有効で一貫性のある「事実」のみが記録されることを目指します。

具体的には、
* `RecordTransactionCommand` のバリデーション（例: 金額が適切な数値範囲であるか、必須項目が全て入力されているかなど）は、コマンドがドメインモデルに渡される前に行います。
* バリデーションに失敗した場合、Discord Botのインターフェースを通じてユーザーに適切なエラーメッセージを返します。
* これにより、不正確なデータがイベントストアに永続化されるのを防ぎ、システムの整合性を高めます。

**【MVP後の計画】**

アカウントおよびタグの作成・管理機能は、MVPの完了後、次の開発フェーズにおける最優先事項として、プロジェクト全体のEvent Sourcing + CQRSアーキテクチャに則って実装を進める予定です。これに関する具体的な設計方針は、別途「アカウントおよびタグ管理機能の設計方針」ドキュメントにて定義します。また、実装の詳細は[feat: アカウントおよびタグ管理機能の実装](https://github.com/your-org/your-repo/issues/X) (※実際のIssue番号に置き換えてください) としてIssueを起票し、管理します。
